# عقد مصدر تشخيص مطابقة المخزون الموحد

> الحالة: معتمد بتاريخ 2026-09-13
>
> التاريخ: 2026-09-13
>
> الفرع: `feature/inventory-control-staging`
>
> النطاق: تصميم فقط — لا Migration ولا تغيير واجهة أو بيانات

## 1. الهدف

إنشاء مصدر واحد داخل PostgreSQL يجيب بصورة متسقة عن ثلاثة أسئلة مختلفة:

1. هل كمية بطاقة المنتج تساوي صافي حركاته؟
2. هل القيمة الدفترية في الحركات سليمة لكل منتج؟
3. هل صافي قيمة الحركات يساوي رصيد حساب المخزون `1104`، وهل يمكن تفسير كل أثر بمستند؟

لا يجوز دمج الأسئلة الثلاثة في فرق واحد؛ فقد يكون الإجمالي صفراً بسبب مقاصة أخطاء متعاكسة بينما توجد مستندات أو منتجات غير سليمة.

## 2. مصدر الحقيقة المحاسبي

### 2.1 الكمية

- كمية الحركة الموقعة تُحسب حصراً بواسطة قاعدة موحدة لأنواع الحركات.
- كمية البطاقة `products.quantity_on_hand` قيمة تشغيلية للمقارنة، وليست بديلاً عن سجل الحركات.
- `quantity_difference = card_quantity - movement_quantity`.
- لا تستخدم أرقام JavaScript في الحساب النهائي.

### 2.2 القيمة

- `movement_book_value` = مجموع قيمة كل الحركات المسجلة بإشارتها المحاسبية.
- `ledger_1104_balance` = مجموع `debit - credit` لسطور الحساب `1104` في القيود المرحلة فقط.
- `movement_to_ledger_difference = ledger_1104_balance - movement_book_value`.
- `wac_valuation` يبقى مؤشراً تحليلياً مستقلاً، ولا يُسمى رصيداً دفترياً ولا يستبدل قيمة الحركات.
- تكلفة الوحدة الدفترية المستخدمة لاحقاً في التسوية = `movement_book_value ÷ movement_quantity` عندما تكون الكمية غير صفرية والقيمة سليمة.

### 2.3 عدم توزيع الحساب العام على المنتجات

سطور `1104` الحالية مجمعة غالباً على مستوى المستند ولا تحمل `product_id`. لذلك لا ينسب النظام رصيد الأستاذ إلى منتج بعينه بالتخمين. المطابقة تكون على محورين:

- محور المنتج: البطاقة والحركات والقيمة.
- محور المصدر: مجموع حركات المستند مقابل سطر أو سطور `1104` في قيده.

ثم يطابق الإجمالي العام بين كل الحركات وكل سطور `1104`.

## 3. نطاق البيانات

- الإصدار الأول تشخيص للحالة المسجلة الآن فقط، ولا يقبل مرشح تاريخ.
- سبب القيد أن `products.quantity_on_hand` لا يملك تاريخ تغييرات كاملاً يسمح بإعادة بناء كمية البطاقة في تاريخ سابق.
- تشمل المطابقة كل حركات المخزون المسجلة وكل قيود `1104` المرحلة، حتى لا يظهر فرق وهمي إذا رُحل مستند مؤرخ لاحقاً لكنه أثر فعلياً في البطاقة.
- يبقى التقييم التاريخي متاحاً في تقرير تقييم المخزون، لكنه لا يصدر قرار إصلاح لرصيد البطاقة.
- تشمل المنتجات النشطة وغير النشطة إذا كان لها رصيد بطاقة أو حركة أو قيمة غير صفرية.
- يظهر المنتج بلا حركة إذا كانت كمية بطاقته غير صفرية.
- لا تدخل قيود المسودة أو الملغاة في رصيد `1104`.
- لا تختفي المستندات الملغاة؛ تُعرض آثارها الأصلية والعكسية كمجموعة واحدة متى كان رابط العكس مثبتاً.

## 4. الربط الحتمي بالمستندات

يبنى سجل مصادر موحد داخل الاستعلام من العلاقات الصريحة التالية:

| نوع المرجع | جدول المصدر | رابط القيد |
|---|---|---|
| `sales_invoice` | `sales_invoices` | `journal_entry_id` |
| `purchase_invoice` | `purchase_invoices` | `journal_entry_id` |
| `sales_return` | `sales_returns` | `journal_entry_id` |
| `purchase_return` | `purchase_returns` | `journal_entry_id` |
| `adjustment` | `inventory_adjustments` | `journal_entry_id` |
| `inventory_adjustment` | `inventory_adjustments` | توافق للسجلات القديمة |
| `staging_seed` | القيد المشار إليه مباشرة | `inventory_movements.reference_id = journal_entries.id` |

بالنسبة إلى `opening_balance` الحالي:

- إذا كان `reference_id` فارغاً فلا يُخمن القيد بالوصف أو التاريخ أو المبلغ.
- يصنف الأثر «غير موثق» ويعرض مرشحين للمراجعة فقط في المعالج لاحقاً.
- كل رصيد افتتاحي جديد بعد التطوير يجب أن يحمل مرجعاً صريحاً إلى مستند افتتاح أو قيد معروف.

ربط القيود العكسية:

- يستخدم `audit_log.new_data.reversal_journal_entry_id` عندما يكون الحدث موثقاً ومصدره معروفاً.
- لا يعتمد وصف القيد للربط الآلي.
- القيد العكسي غير المرتبط صراحة يبقى «قيداً بلا حركة/مرجع» ولا يُخفى لمجرد أن قيمته تعاكس قيداً آخر.

## 5. التصنيفات الأساسية

يحمل كل انحراف `classification` واحداً من القيم التالية:

| الرمز | المعنى | شرط نموذجي |
|---|---|---|
| `product_balance` | رصيد منتج | كمية البطاقة لا تساوي صافي الحركات |
| `movement_without_journal` | حركة بلا قيد | مصدر معروف له قيمة حركة ولا يملك قيداً مرحلاً أو سطر `1104` |
| `journal_without_movement` | قيد بلا حركة | أثر `1104` موثق لمصدر بلا حركات مقابلة، أو قيد مخزون مستقل غير مفسر |
| `undocumented_effect` | أثر غير موثق | مرجع فارغ/مجهول/مفقود، حالة مستند متناقضة، أو قيم غير منطقية |
| `rounding` | باقي تقريب | المصدر والحركة والقيد موجودة، والفرق غير الصفري قابل للإسناد لتقريب المستند |

ويحمل `reason_code` تفصيلياً، ومنه:

- `card_without_movements`
- `movements_not_applied_to_card`
- `missing_reference_id`
- `unknown_reference_type`
- `missing_source_document`
- `missing_journal_entry`
- `journal_not_posted`
- `missing_1104_line`
- `posted_source_without_movements`
- `cancelled_source_not_fully_reversed`
- `unlinked_reversal`
- `source_value_mismatch`
- `zero_quantity_nonzero_value`
- `nonzero_quantity_zero_value`
- `negative_book_unit_cost`
- `traceable_rounding_residual`

التصنيف يصف السبب ولا ينفذ إصلاحاً.

## 6. قواعد التقريب

- العمليات الحسابية تتم بنوع `numeric` داخل PostgreSQL.
- الكميات لا تُقارن بتسامح عائم؛ تُقارن بعد مقياس الكمية الفعلي المخزن.
- العملة تُعرض بمنزلتين، لكن الفرق `0.01` لا يُخفى ولا يسمى مطابقاً.
- يصنف الفرق كتقريب فقط إذا كان للمصدر مستند وقيد وحركات معروفة، وكان الفرق المطلق لا يتجاوز `0.01` لكل مستند، ولا توجد مشكلة هيكلية أخرى.
- مجموع بقايا التقريب يعرض إجمالياً دون مقاصة بينها وبين أخطاء أخرى.
- الحالة `matched` تعني صفراً فعلياً بعد التقريب المحاسبي إلى منزلتين، لا مجرد الوقوع داخل حد واسع.

## 7. واجهة قاعدة البيانات المقترحة

دالة عامة واحدة للقراءة:

```sql
public.get_inventory_reconciliation_diagnostic(
  p_section text DEFAULT 'summary',
  p_only_issues boolean DEFAULT true,
  p_search text DEFAULT NULL,
  p_limit integer DEFAULT 100,
  p_offset integer DEFAULT 0,
  p_expected_fingerprint text DEFAULT NULL
) RETURNS jsonb
```

الأقسام المقبولة:

- `summary`: الإجماليات والعدادات فقط.
- `products`: صفوف محور المنتجات بصفحات.
- `sources`: صفوف المستندات والقيود والحركات بصفحات.

كل استدعاء يعيد:

```text
schema_version
snapshot_at
source_scope
fingerprint
status
totals
issue_counts
page
rows
```

قواعد الاستدعاء:

- الحد الأدنى `1` والأقصى `500` صف في الطلب.
- `p_offset` غير سالب.
- البحث يتم داخل قاعدة البيانات بالكود والاسم ورقم المستند.
- الاستدعاء الأول يعيد `fingerprint`.
- ترسل الواجهة البصمة في الصفحات التالية؛ إذا تغيرت البيانات ترفض الدالة الطلب برمز `RECONCILIATION_SNAPSHOT_STALE` وتعيد الواجهة تحميل التقرير.
- الدالة `STABLE` و`SECURITY DEFINER` مع `search_path` ثابت وأسماء مؤهلة بالكامل.
- تستدعي `require_finance_api_access()`؛ المدير والمحاسب فقط، ولا تصل التكلفة إلى البائع.
- تُسحب صلاحية التنفيذ من `PUBLIC` و`anon` وتمنح لـ`authenticated` و`service_role` مع استمرار فحص الدور داخل الدالة.

## 8. عقد الملخص

يعيد `summary` على الأقل:

```text
card_quantity
movement_quantity
quantity_difference
movement_book_value
wac_valuation
ledger_1104_balance
movement_to_ledger_difference
wac_to_movement_difference
wac_to_ledger_difference
product_issue_count
source_issue_count
rounding_issue_count
unlinked_movement_count
unlinked_journal_count
```

ويعيد `status` إحدى القيم:

- `matched`: لا فرق كمية ولا قيمة ولا روابط مجهولة.
- `rounding_only`: لا توجد مشكلة سوى بقايا تقريب موثقة.
- `mismatch`: يوجد انحراف غير التقريب.
- `unavailable`: تعذر حساب مصدر أساسي مثل الحساب `1104`.

لا تعتمد الحالة على صافي الفرق وحده؛ وجود انحرافين متعاكسين يبقي الحالة `mismatch`.

## 9. عقد صف المنتج

كل صف في قسم `products` يعيد:

```text
product_id, code, name, is_active
card_quantity, movement_quantity, quantity_difference
movement_book_value, book_unit_cost
wac, wac_valuation, wac_to_movement_difference
last_movement_date, movement_count
classification, reason_codes
can_prepare_repair
```

`can_prepare_repair` معلومة أهلية فقط، ولا تعني أن الواجهة تستطيع الكتابة. تكون `false` عند القيمة بلا كمية، أو التكلفة الصفرية غير المفسرة، أو مرجع غير معروف، أو تغير البصمة.

## 10. عقد صف المصدر

كل صف في قسم `sources` يعيد:

```text
source_type, source_id, source_number, source_status, source_date
journal_entry_id, reversal_journal_entry_id
movement_count, movement_quantity, movement_book_value
ledger_1104_value, source_difference
classification, reason_codes
is_rounding_only
can_prepare_repair
```

تستخدم الإشارة نفسها للطرفين: زيادة أصل المخزون موجبة ونقصه سالب. لا تُجرى مقاصة بين مصادر مختلفة عند التصنيف.

## 11. البصمة ومنع القرار القديم

تحسب البصمة من المحتوى المؤثر نفسه، وليس من عدد الصفوف فقط:

- معرف المنتج و`quantity_on_hand` و`updated_at`.
- حقول الحركة المؤثرة: المعرف والنوع والكمية والقيمة والتاريخ والمرجع.
- قيود `1104` المرحلة: معرف القيد وحالته وتاريخه ومعرف السطر والمدين والدائن.
- حالة وروابط المستندات المعروفة.
- روابط العكس الموثقة.

تُرتب المدخلات ترتيباً حتمياً ثم تُجزأ. عند إنشاء مسودة معالجة لاحقاً تحفظ البصمة، ويعاد حسابها داخل معاملة التنفيذ؛ تغيرها يمنع التنفيذ بدلاً من تطبيق اقتراح قديم. يمثّل `source_scope` القيمة الثابتة `all_recorded_stock_effects` حتى لا تلتبس هذه الشاشة مع تقرير التقييم التاريخي.

## 12. الفصل بين القراءة والإصلاح

- دالة التشخيص للقراءة فقط ولا تحدث أي جدول.
- لا تعيد الدالة SQL قابلاً للتنفيذ ولا تسمح بتمرير اسم جدول أو حساب.
- زر «مزامنة» الحالي لا يستخدم بعد تفعيل المصدر الجديد، ويزال فقط بعد جاهزية مستند المعالجة.
- اختيار الإصلاح ينشئ لاحقاً مسودة مستقلة في جداول المعالج، ولا يعدل التقرير مباشرة.
- المحاسب يعد مسودة الإصلاح، والمدير وحده ينفذ أو يعكس وفق القرار المعتمد.

## 13. الأداء والفهارس

- لا تُرسل جداول الحركات كاملة إلى المتصفح.
- تستخدم الدالة تجميعاً واحداً للحركات وتجميعاً واحداً لسطور `1104`.
- يعاد استخدام الفهارس الحالية على المنتج والتاريخ والمرجع، ويُضاف فقط ما يثبته `EXPLAIN` على نسخة Staging.
- الفهارس المرشحة للمراجعة وليست معتمدة تلقائياً:
  - `inventory_movements (movement_date, product_id)`.
  - `inventory_movements (reference_type, reference_id)`.
  - `journal_entries (status, entry_date, id)`.
  - `journal_entry_lines (account_id, journal_entry_id)`.
- يمنع `p_limit > 500`، ويعاد `total_count` للصفحات.
- تختبر الخطة على بيانات Staging الحقيقية مع `EXPLAIN (ANALYZE, BUFFERS)` داخل قراءة فقط قبل اعتماد أي فهرس.

## 14. التوافق

- تبقى `get_inventory_valuation` دون حذف في هذه المرحلة.
- لا تغير الشاشة مصدرها قبل نشر الدالة واختبارها جنباً إلى جنب.
- يقارن اختبار ظل النتائج الجديدة مع الأرقام الحالية، ويشرح الفروق بدلاً من فرض تطابق خاطئ بين `WAC` وقيمة الحركات.
- يدعم `adjustment` و`inventory_adjustment` خلال فترة التوافق.
- القيم أو المراجع التاريخية غير القابلة للربط لا تُعدل آلياً؛ تظهر كحالات تحتاج مراجعة.

## 15. اختبارات القبول قبل Migration

يجب أن يغطي اختبار التصميم القادم على الأقل:

1. منتج مطابق بالكامل.
2. كمية بطاقة بلا حركة.
3. حركة لم تُطبق على البطاقة.
4. حركة مصدر معروف بلا قيد.
5. قيد `1104` بلا حركة.
6. مستند له الطرفان مع اختلاف قيمة أكبر من سنت.
7. فرق سنت واحد موثق كتقريب، لا كمطابقة.
8. حركة بلا `reference_id`.
9. نوع مرجع مجهول.
10. مستند ملغي مع عكس صحيح.
11. عكس غير مرتبط.
12. كمية صفر وقيمة غير صفرية والعكس.
13. منتج غير نشط له رصيد.
14. تغير البيانات بين صفحتين ورفض البصمة القديمة.
15. رفض وصول البائع ونجاح المدير والمحاسب.
16. تطابق الملخص مع جمع كل الصفوف بلا تأثير للصفحات أو البحث.

## 16. ترتيب التنفيذ بعد الاعتماد

1. كتابة اختبارات SQL للعقد الجديد أولاً بحيث تفشل لغياب الدالة.
2. إنشاء Migration للدالة فقط، دون جداول إصلاح ودون تعديل الواجهة.
3. تشغيلها على قاعدة L3 المعزولة.
4. أخذ نسخة حديثة من Staging وخط أساس قبل التطبيق.
5. تطبيق Migration على Staging فقط.
6. تشغيل مقارنة ظل read-only بين المصدر القديم والجديد.
7. بعد اعتماد النتائج، ربط شاشة التشخيص بالدالة الجديدة وإلغاء التجميع داخل المتصفح.
8. يبدأ تصميم جداول المعالج وعمليات الإصلاح الذرية كبند مستقل.
