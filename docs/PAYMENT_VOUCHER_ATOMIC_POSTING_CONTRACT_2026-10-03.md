# عقد ترحيل سندات القبض والصرف ودفعات المستندات ذريًا

التاريخ: 2026-10-03. هذا عقد تنفيذ للمرحلة 2 من [الخطة الرئيسية](SYSTEM_STABILITY_MASTER_PLAN_2026-10-01.md)، مبني على [مصفوفة السندات](SYSTEM_STABILITY_STAGE1_DOCUMENT_PAYMENT_MATRIX_2026-10-03.md) واختبارات الفشل RED. **الحالة: تصميم محدد، لم يُنفذ Migration أو يُنشر.** لا يجيز هذا العقد تغيير أي قاعدة مستضافة. إلغاء سند مرحّل له [عقد مستقل](PAYMENT_VOUCHER_ATOMIC_CANCELLATION_CONTRACT_2026-10-03.md) ولا يُخلط بهذا الإصدار.

## حدود الحدث الواحد

المدخلات المسموحة: نوع الطرف `customer|supplier`، معرّف الطرف، تاريخ محاسبي، مبلغ موجب بدقة العملة، وسيلة دفع معتمدة، مرجع وملاحظات، معرّف مسودة اختياري، ومصدر اختياري واحد من `sales|purchase|sales_return|purchase_return` مع معرّفه، ومفتاح طلب UUID يولده العميل مرة واحدة ويعيد استخدامه عند إعادة المحاولة. لا يقبل الخادم رقم السند أو القيد، بادئة العرض، اسم الطرف، أرصدة، سطور قيد، أو مبلغ متبقٍ من المتصفح.

تُعرض دالتا API `post_customer_payment_atomic` و`post_supplier_payment_atomic` بتوقيع ثابت لكل منهما، وتستدعيان تنفيذًا داخليًا مشتركًا لا يملك المستدعي حق تمرير اسم جدول إليه. لا تُمنح دالة الداخل لأدوار API. كل استدعاء PostgREST/RPC هو **معاملة واحدة**: لا يُسمح بإنشاء القيد ثم طلب آخر لحفظ السند أو التخصيص أو الرصيد. تستبدل واجهتا السند وقسم مدفوعات الفاتورة/المرتجع المسارات المنفصلة باستدعاء واحد؛ لا يظهر نجاح قبل اكتمال النتيجة الخادمية.

| نوع المصدر | جدول السند | جدول التخصيص | اتجاه القيد: مدين / دائن |
| --- | --- | --- | --- |
| بلا مصدر، عميل | `customer_payments` | لا تخصيص | نقدية 1101/1102 / ذمم العملاء 1103 |
| بلا مصدر، مورد | `supplier_payments` | لا تخصيص | ذمم الموردين 2101 / نقدية 1101/1102 |
| `sales` | `customer_payments` | `customer_payment_allocations` | نقدية / ذمم العملاء |
| `purchase` | `supplier_payments` | `supplier_payment_allocations` | ذمم الموردين / نقدية |
| `sales_return` | `customer_payments` | `sales_return_payment_allocations` | ذمم العملاء / نقدية |
| `purchase_return` | `supplier_payments` | `purchase_return_payment_allocations` | نقدية / ذمم الموردين |

هذه الخريطة مأخوذة من `postPaymentVoucher` و`InvoicePaymentSection.handleNewPayment` الحاليين؛ لا تعني اعتماد أرقام الحسابات إن كانت هوية الحساب أو إعداد الشركة مختلفة في قاعدة حديثة. يعتمد التنفيذ على هوية الحساب النشط الورقي وفق العقد المحاسبي الحالي، ويرفض غيابه أو تعطيله. **لا يُستنتج اتجاه دفعة مرتجع من جدول السند وحده**؛ نوع المصدر والقيد المحاسبي والتخصيص يجب أن يتطابقوا، ويُمنع إعادة ربط سند عادي بمرتجع بطريقة تغيّر دلالته بصمت.

## تسلسل الحماية الخادمية

1. تحقق هوية `auth.uid()` ودور الأعمال خادميًا، وطابق نوع الطرف مع نوع المصدر. اربط طلب إعادة المحاولة بمفتاح فريد لكل شركة/نوع سند مع بصمة مدخلات كاملة؛ نفس المفتاح ونفس البصمة يعيدان **النتيجة السابقة نفسها**، أما إعادة المفتاح بمدخلات مختلفة فترفض. يُخزَّن المفتاح والنتيجة داخل المعاملة نفسها، فلا تبقى علامة نجاح بلا سند.
2. اقفل المسودة إن وجدت وتحقق `status='draft'` ورابط الطرف وعدم وجود قيد/رقم مرحّل، ثم احفظ تعديل حقولها وترحيلها في **الدالة نفسها**. لا تسبق الواجهة ذلك بطلب `savePaymentVoucherDraft` منفصل. إذا لم يصب التحديث صفًا واحدًا بالضبط، ارفض العملية. المسودة غير الموجودة أو المرحّلة ليست إنشاءً جديدًا بديلًا.
3. اقفل الطرف والمستند المصدر إن وجد بترتيب ثابت، وتحقق من حالة ترحيله وهوية العميل/المورد والتاريخ والفترة المقفلة. احسب المتبقي من مجموع التخصيصات والتسويات الصحيحة في القاعدة، لا من `invoiceTotal` أو `remaining` في الواجهة. ارفض المبلغ غير الصحيح أو الذي يتجاوز المتبقي، بما في ذلك طلبان متزامنان للمستند نفسه.
4. احجز رقم السند داخل القاعدة بآلية متسلسلة/قفل مخصص لكل نوع مع فهرس فريد للأرقام المرحّلة. لا يُستعمل `MAX+1` من المتصفح. البادئة تُقرأ من `company_settings` للعرض فقط، ولا تُحفظ كقيمة ثابتة في Migration. استدعِ بوابة `create_journal_entry` القائمة مع `p_posted_number=NULL` كي تخصص **رقم القيد** خادميًا تحت حارسها الحالي، بعد اختبار توافقها على PG15 وPG17.
5. اكتب القيد المتوازن والسند والتخصيص الاختياري وحقول `paid_amount`/رصيد الطرف المتأثرة في المعاملة ذاتها. حساب الرصيد لا يعتمد على جلب PostgREST محدود بألف صف؛ يستخدم تجميع SQL خادميًا موثقًا يتضمن أثر دفعات المرتجعات مرة واحدة ويطابق الأستاذ ضمن تعريف التقرير. لا تكتب شاشة القراءة `paid_amount`. أي خطأ أو صفر صفوف متوقع أو اختلاف البصمة يُفشل المعاملة كاملة.
6. أعد `payment_id`, `posted_number`, `journal_entry_id`, `request_id` فقط بعد التحقق من أن القيد مرحّل ومتوازن، وأن السند مرحّل ويرتبط به، وأن التخصيص والمبلغ والرصيد مطابقان. لا تُعاد رسالة نجاح من المتصفح عند `error` أو نتيجة فارغة.

## قيود وقارئات لا يجوز تجاوزها

- فهرس تفرد `posted_number` لسند العميل مستقل عن سند المورد، مع السماح بـ`NULL` للمسودة. تُفحص التكرارات التاريخية في كل قاعدة قبل إنشاء الفهرس؛ لا تُصلح أرقامها ضمن هذا الترحيل المشترك بلا قرار منفصل.
- تُحفظ وظيفة إنشاء القيد الحالية وحارس رقم القيد؛ لا تُعدَّل Migration مطبقة. إذا كشفت تجربة PG15/PG17 أن بوابة القيد لا تفحص الفترة أو الحسابات بما يكفي، يُضاف حارس جديد واختبار رجوع خاص قبل استخدام RPC.
- يُمنع مسار الكتابة المباشرة الموازي لترحيل السند وإدراج تخصيصه بعد جاهزية جميع الواجهات، مع إبقاء حفظ المسودة وربط سند مرحّل قائم وفق سياسة مستقلة ومختبرة. تُفحص أدوار المدير والمحاسب والبائع والمجهول و`service_role` عبر API، لا RLS المصدر وحده.
- تُعدّل قراءات قائمة السندات والأطراف والتخصيصات كي لا تخفي خطأ قراءة أو تعرض نتيجة ناقصة، وترتب الصفحات ترتيبًا فريدًا. لا تُضاف كتابة رصيد أثناء فتح الشاشة. تُفحص وظيفة توليد بيانات الاختبار والاستعادة قبل تقييد الكتابة حتى لا يبقى مسار قديم صامت.
- لا يدخل تعديل السند المرحّل أو إلغاؤه في هذه الدالة؛ يُعالجان بعقدي تعديل/عكس منفصلين مع أثر تاريخي. لا يُعاد ترقيم مستند قديم ولا تُغيّر بيانات إنتاج سابقة بهذا العمل.

## اختبارات القبول والرجوع قبل Staging

| الاختبار | النجاح المطلوب |
| --- | --- |
| ست رحلات الجدول أعلاه، مع مسودة جديدة وموجودة | سند واحد، قيد واحد متوازن، تخصيص واحد عند الحاجة، واتجاه صحيح ورصيد مطابق |
| فشل مُحقن بعد إنشاء القيد، وبعد السند، وبعد التخصيص، وعند تحديث الرصيد | لا يبقى قيد أو سند أو تخصيص أو رقم أو تعديل رصيد؛ بصمات الجداول غير المستهدفة ثابتة |
| مسودة مفقودة/مرحّلة، مصدر غير مرحّل، مبلغ فوق المتبقي، حساب مفقود، فترة مقفلة | رفض صريح قبل أثر دائم؛ لا نجاح صفري ولا افتراض قيمة صفر عند فشل قراءة |
| طلبان متزامنان للمستند أو رقم السند، وإعادة نفس `request_id` | لا تجاوز للمتبقي ولا رقم مكرر؛ إعادة المفتاح المتطابق تعيد النتيجة نفسها، والمختلف يرفض |
| 1,001 ثم 10,000 سند/تخصيص وPG15 وPG17 | الحساب كامل، الرقم فريد، زمن/ذاكرة مقاسان، لا نتيجة جزئية عند صفحة ناقصة |
| أدوار API الحقيقية وكتابة مباشرة بعد التحويل | العملية الشرعية متاحة لدورها، والترحيل المباشر أو تعديل سند مرحّل من خارج RPC مرفوض دون تعطيل المسودة |

الترتيب التنفيذي: عقد SQL أحمر على مخطط حديث معزول؛ Migration جديدة + ملف رجوع صريح؛ اختبارات ذرية/تزامن/أدوار على PG15 وPG17؛ توصيل **كلتا** واجهتَي السند وقسم الفاتورة/المرتجع؛ اختبار قراءة/تصدير؛ نسخة Staging حديثة وتجربة ترحيل ورجوع وقبول؛ ثم قرار نشر مستقل لاحقًا لكل شركة. لا يُنفّذ على Staging أو الإنتاج بالموافقة العامة على هذه الخطة وحدها.

الرجوع قبل أي نشر: إرجاع تغييرات الفرع فقط. بعد تطبيق تجريبي **وقبل** أول سند جديد: ملف الرجوع الصريح يعيد الواجهات والدوال والأذونات مع بقاء البيانات القديمة. إذا وُجدت سندات جديدة عبر العقد فلا تُحذف قيودها أو أرقامها؛ يُوقف المدخل الجديد ويُراجع أثرها وخطة رجوع محاسبية موثقة. لا رجوع إنتاجي تلقائي.
