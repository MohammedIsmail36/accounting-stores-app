## نطاق المرحلة

تنقل L7 الواجهتين بالتتابع من المصدر القديم إلى المستودع النظيف `accounting-stores-app`. يبدأ الانتقال بـFarida وحدها بعد نسخة رجوع واختبار جاف، ولا تبدأ Alibea قبل اعتماد Farida. لا تشمل هذه الدفعة أي migration أو تعديل قاعدة بيانات أو Edge Functions.

## الحالة المرجعية قبل Farida

- بقي checkout الإنتاج القديم `/opt/accounting-app` وremote القديم بلا تغيير.
- حُفظت نسخة ملفات Farida في `/opt/backups/accounting-app/farida-l7-new-repo-before-20260908`.
- طابق عدد ملفات النسخة المرجعية عدد ملفات الموقع: 183 ملفاً.
- بصمة `index.html` المرجعية: `81b00744793d06a2641ef6b2380dec5a9eb56e8ef29418b88173653fa4cda388`.
- أثبت الفحص أن Nginx والخدمات وقواعد Farida وAlibea وEdge Functions لا تعتمد تشغيلياً على مسار checkout القديم.

## حادثة محاولة النشر الأولى

استُدعي سكربت النشر بمتغير Farida مأخوذ من ملف dotenv بواسطة استخراج نصي خام. كانت القيمة في الملف محاطة بعلامتي اقتباس؛ لذلك أصبح طول النص الخام 210 محارف، بينما القيمة التي يفسرها shell بواسطة `source` طولها 208 محارف. دخلت علامتا الاقتباس في حزمة المتصفح وأصبحت ترويسة API غير صالحة.

النتيجة الظاهرة كانت `401 Unauthorized` لطلب `company_settings` ولمسار تسجيل الدخول. هذا لا يدل على فقد بيانات أو تغيير قاعدة، ولم يكن سببه المستودع الجديد أو Supabase نفسه. أزيلت علامات الاقتباس في الاختبار التالي، لكن اتضح لاحقاً أن مصدر المفتاح نفسه غير صحيح أيضاً كما هو موثق أدناه.

## محاولة النشر الثانية واكتمال التشخيص

بعد إضافة حاجز الصيغة وتثبيته في الالتزام `a6e5420`، نجح البناء الجاف من clone مستقل. نُشرت واجهة Farida فقط بخيارات تمنع `git pull` وmigrations وEdge Functions. نجح بناء Vite ومطابقة الأصل المنشور، لكن فحص API المستقل أعاد 401؛ لذلك استُعيدت النسخة المرجعية فوراً مرة ثانية.

أثبتت مقارنة البصمات دون طباعة القيم أن المفتاح المحمّل من `/opt/accounting-app/.env` طوله 208 محارف ولا يطابق مفتاح البناء المرجعي، بينما `ANON_KEY` في `/opt/supabase-farida/docker/.env` طوله 169 محارف ويطابق المفتاح الفعلي في البناء المرجعي تماماً. إذن `.env` القديم ليس مصدراً صالحاً لنشر Farida حتى لو حُمّل بواسطة `source`.

بعد الرجوع الثاني عادت بصمة `index.html` إلى `81b00744793d06a2641ef6b2380dec5a9eb56e8ef29418b88173653fa4cda388`، وأعاد `/auth` الحالة 200 وأعاد طلب `company_settings` بالمفتاح المرجعي الحالة 200.

## الرجوع والتحقق

- أُوقف الانتقال ولم تُلمس Alibea.
- استُعيدت نسخة Farida المرجعية إلى `/var/www/farida` باستخدام `rsync --delete-delay --delay-updates`، وثُبت وضع الجذر `0755`.
- عادت بصمة `index.html` مطابقة تماماً للبصمة المرجعية أعلاه.
- أعاد `/` و`/auth` الحالة 200، وأعاد REST بالمفتاح المحمّل بصورة صحيحة الحالة 200.
- أعادت محاولة دخول ببيانات اعتماد غير صحيحة الحالة 400 بدلاً من 401، ما يثبت قبول مفتاح API بعد الرجوع.
- أكد المستخدم أن الدخول إلى Farida يعمل من جديد.
- لم تُطبق migrations، ولم تتغير Edge Functions أو Nginx أو Docker أو قواعد Farida وAlibea.

## الحماية المضافة

أضيف فحص مبكر إلى `scripts/deploy-all.sh` يعمل قبل `git pull` أو migrations أو Edge Functions أو تثبيت الحزم أو البناء. يوقف السكربت عند أي من الحالات التالية:

- متغير المفتاح غير موجود أو فارغ.
- القيمة تبدأ أو تنتهي بعلامة اقتباس مفردة أو مزدوجة.
- القيمة تحتوي مسافة أو محرف سطر.
- القيمة لا تطابق صيغة JWT العامة القديمة أو بادئة `sb_publishable_` الحديثة.
- قبول الصيغة مع رفض API المستهدف للمفتاح أو تعذر الاتصال به؛ يجب أن يعيد طلب `company_settings` الحالة 200.

نجحت اختبارات الصيغة السلبية الأربعة، ورفض اختبار الاتصال مفتاحاً صحيح الصيغة تابعاً لمصدر آخر بالحالة 401 قبل تثبيت الحزم، وقَبِل مفتاح Farida المحمي ثم أكمل البناء الجاف. نجح أيضاً `bash -n` للسكربت.

## إعادة الاختبار الجاف

حُمّل ملف البيئة القديم بواسطة `source` من دون طباعة المفتاح، ثم شُغّل بناء Farida في وضع `--dry-run` داخل clone مستقل من المستودع الجديد. أثبت هذا الاختبار سلامة التضمين فقط، واتضح بعد النشر أنه غير كافٍ قبل إضافة فحص API:

- اكتمل تثبيت 638 حزمة، وفحص npm عدد 639 حزمة بصفر ثغرات.
- أنشأ Vite حزمة الإنتاج وظهر المفتاح المحمّل في أصل واحد فقط؛ لم يكن هذا دليلاً على قبول API له.
- ظهر عنوان `https://farida.alibea2020.com/api` في أصل واحد فقط.
- لم يظهر عنوان أو معرف يخص Alibea أو Staging أو مشروع Supabase التجريبي.
- بقي checkout الاختبار نظيفاً.
- لم تتغير ملفات Farida الحية؛ بقيت بصمة `index.html` المرجعية كما هي واستجاب `/auth` بالحالة 200.

## مصدر النشر المحمي

- اعتُمد إعداد Supabase الذاتي للشركة مرجعاً للتحقق من مفتاحها، بعد مطابقته بالبناء الإنتاجي العامل دون طباعة القيمة.

## الحالة الحالية

## الخطوات التالية بالترتيب

1. تحديث clone معزول إلى الالتزام المدفوع وإعادة `--dry-run --only farida` باستخدام `/etc/accounting-stores-app/deploy.env` حصراً.

3. اختبار الدخول والصلاحيات والشاشة الحرجة وAPI وسجل المتصفح، ثم طلب اعتماد المستخدم.
