# الخطة التشغيلية الشاملة لاستقرار نظام المحاسبة

التاريخ: 2026-10-01. الحالة: **المرحلة 1 — الجرد المعماري جارٍ؛ لا تفويض لتغيير الإنتاج أو تنظيف الملفات**.

هذه الوثيقة هي مرجع ترتيب العمل وقواعده وسجل تقدمه. تحفظ الخطط الأخرى التفاصيل والأدلة التاريخية، ولا تصبح المرحلة التالية لمجرد أن مستندًا قديمًا ذكرها. عند تعارض حالة قديمة مع الواقع، نتوقف عن العمل المتأثر، نثبت الحالة بالدليل، ثم نحدث السجل. لا تمحو هذه الوثيقة تاريخ [الخطة الرئيسية السابقة](MASTER_EXECUTION_PLAN.md) أو [خطة الجرد](خطة-تطوير-مستند-الجرد-وتسوية-المخزون-2026-09-10.md). توجد محليًا أيضًا خطتا QUERY_PAGINATION_INTEGRITY_AND_SCALING_EXECUTION_PLAN_2026-09-28.md وHISTORICAL_FINANCIAL_AND_INVENTORY_RECONCILIATION_PLAN_2026-10-01.md؛ لم تُرفعا إلى Git العام حتى تُراجع تفاصيل الإنتاج فيهما، فلا تفترض وجودهما في الفرع البعيد.

## الهدف وحدود التفويض

الهدف هو كشف نقاط ضعف **النظام كله**، إصلاح أسباب الأخطاء الجديدة بكود مشترك صحيح، إثباته على Staging ونسخ إنتاج معزولة، ثم نشره تدريجيًا. بعد ذلك تعالج الأخطاء التاريخية لكل شركة على حدة، ويُوحد إصدار PostgreSQL في مشروع بنية مستقل. يُراجع تراكم `docs` و`scripts` دون فقد أدلة التدقيق أو ملفات الرجوع.

القبول بهذه الخطة لا يجيز تلقائيًا تطبيق SQL أو تصحيح بيانات إنتاج، استعادة نسخة فوق Staging المشتركة، ترقية PostgreSQL، فتح أو إغلاق خدمات، نشر واجهات، حذف ملفات، أو دمج الفرع في `main`. تُحدد الموافقة والنطاق لكل نافذة تشغيلية على حدة.

## قواعد العمل: تُراجع عند بداية **كل خطوة**

1. **اقرأ قبل التنفيذ:** هذه الوثيقة كاملة، آخر سطر في سجل التقدم، حالة Git، والعقد المتخصص للوظيفة. أعلن للمستخدم المرحلة والخطوة، الحالة المثبتة، البيئة، ما سيتغير وما لن يتغير، اختبار النجاح، وحد الرجوع.
2. **حقيقة لا تخمين:** صنّف كل ملاحظة: خلل مُعاد إنتاجه، خطر تصميم يحتاج اختبارًا، فرق تاريخي مؤكد، أو سلوك مقصود. اربطها بمصدر وبيانات اختبار ونتيجة. لا تسمِّ الشك خطأً إنتاجيًا.
3. **شركة مستقلة:** Farida وAlibea وStaging ثلاث قواعد وواجهات وهوّيات مختلفة. لا تستعمل مبلغًا أو معرفًا أو نسخة من شركة لتصحيح أخرى، ولا تفترض تطابق Staging مع الإنتاج.
4. **المحاسبة قابلة للتدقيق:** لا تُخفِ فرقًا بتوحيد مصدرين مستقلين أو رفع سماحية التقريب. قارن القيود المرحلة وحركات المخزون وتقييم WAC كلًّا وفق تعريفه ونطاقه وتاريخه. لا تعدل قيدًا أو حركة مرحلة بصمت؛ التصحيح التاريخي بأثر جديد مرتبط بالأصل واعتماد ورجوع مقابل بعد مراجعة محاسبية.
5. **معاملة واحدة للحدث:** ترحيل مستند أو إلغاؤه أو عكسه أو إقفال سنة يتضمن فحص الصلاحية والفترة والتكلفة والترقيم والمستند والحركات والقيود في قاعدة البيانات بعملية ذرية. الواجهة لا تصبح مصدر المبلغ أو قرار الاعتماد. التكرار والتزامن لهما سياسة واضحة.
6. **صلاحية الخادم أولًا:** حماية RLS وRPC وEdge Functions لا تعتمد على إخفاء زر. اختبر المدير والمحاسب والبائع والمجهول على API مباشرة، خصوصًا وظائف الخدمة والاستعادة والدوال ذات `SECURITY DEFINER`.
7. **النتيجة الناقصة فشل:** أي تقرير مالي أو تصدير أو إقفال لا يعلن رقمًا كاملًا من صفحة ناقصة أو طلب فاشل؛ يثبت اكتمال النطاق وترتيبًا فريدًا ولقطة متسقة عند الحاجة. لا يحل رفع حد الصفوف محل التصميم الصحيح.
8. **اختبار متناسب:** اختبار وحدة وعقد قاعدة ونسخة معزولة وStaging وقبول واجهة بحسب الخطر، دون تكرار فحوص متكافئة بلا فائدة. لكل تغيير عالي الأثر فاحص مستقل وحد رجوع مجرّب. تُسجل مدة الفحوص وأسباب بطئها لتحسينها.
9. **النشر مقيد وقابل للفصل:** ترحيلات قبل واجهة تعتمد عليها؛ إصدار مجمد وبصمة ونسخة حديثة قابلة للاستعادة؛ نشر Farida ثم Alibea بموافقة ونوافذ منفصلتين. عدم نجاح بوابة شركة لا يغير الأخرى تلقائيًا. لا يُعاد تشغيل تطبيق جزئي بلا مراجعة الحالة.
10. **Git العام ليس أرشيف نسخ:** لا مفاتيح أو كلمات مرور أو تفريغات DB أو سجلات خام أو بيانات عملاء أو تقارير مالية تفصيلية في الفرع العام. تبقى الأدلة الحساسة في أرشيف محمي خارج المستودع؛ يُرفع ملخص منزوع الحساسية وبصمة إذا لزم. لا تُرفع التغييرات المتراكمة جماعيًا قبل مراجعتها.
11. **لا حذف بلا جرد:** صنّف الملفات «تشغيلي»، «اختبار قابل للإعادة»، «عقد/ترحيل/رجوع»، «دليل تاريخي»، «مؤقت». يُثبت كل اعتماد قبل النقل أو الحذف. لا تعد كتابة Migration مطبقة ولا تحذف دليل رجوع أو نسخة احتياطية بغرض ترتيب المجلد.
12. **التوثيق جزء من الإنجاز:** عند انتهاء كل خطوة حدّث جدول الحالة وسجل التقدم أدناه: تاريخ، فرع/التزام، نطاق، ما تحقق، ما لم يتحقق، البيئة التي تغيرت، مسار التقرير الآمن، والخطوة التالية. لا تُعلن مرحلة «مكتملة» لأن سكربتًا انتهى بنجاح فقط.

### مخرجات المرحلة 1

- قائمة واحدة لكل مسار من: إنشاء، تعديل، حذف مسودة، ترحيل، إلغاء، عكس، ترقيم، استيراد، قراءة، تصدير. يسجل المسار استدعاءات الواجهة وRPC والجداول والمفاتيح والصلاحيات والاختبارات.
- اختبار فشل قبل الإصلاح لكل خلل مثبت، مع بيانات مصطنعة وأثر متوقع، وتصنيف الشدة: حرج للمال أو الصلاحية، عالٍ للبيانات، متوسط للأداء/الواجهة، منخفض للتنظيم.
- قائمة الاعتمادات المتبادلة بين الشركات والترحيلات والواجهات؛ لا يبدأ تنفيذ المرحلة 2 قبل معرفة أي تغيير مشترك وأي تغيير خاص.

### مخرجات المرحلتين 2 و3

- عقد موحد لتوقيت الاعتراف بالمستند والضريبة والتكلفة والتقريب، مع تحقق قاعدة البيانات لا المتصفح. تحفظ البادئات وإعدادات الشركة ولا تثبت في الكود قيم جديدة.
- تحويل العمليات غير الذرية إلى دوال خادمية باختبار تزامن وإعادة محاولة ومعرّف طلب، وعكس محاسبي لا حذف قيد مرحل.
- تدقيق صلاحيات كل RPC وEdge Function وتوثيق مصفوفة السماح؛ اختبار مباشر بأدوار فعلية. يفصل علاج خطر الاستعادة العاجل عن تحسينات الواجهة.
- تقارير خادمية تحسب على كامل النطاق، وتفاصيل بصفحات مرتبة ترتيبًا فريدًا، وحالة خطأ للصفحات الناقصة. تقاس القراءة والكتابة والذاكرة والزمن قبل تعديل الفهارس.

### مخرجات المراحل 4 إلى 8

- تجربة نسخة Farida ثم Alibea في قاعدتين خاصتين معزولتين، مع مقارنة عدد وبصمات السجلات غير المستهدفة. لا تنسخ البيانات إلى Staging المشتركة ولا ترفع البيانات إلى Git.
- إصدار كود مشترك مستقل عن تصحيح التاريخ؛ اختبار PG15 وPG17، ثم نشر Farida وقبولها، ثم قرار مستقل لـAlibea. أي توقف جزئي يُشخَّص من الحالة المحفوظة قبل إعادة المحاولة.
- ترقية PostgreSQL مشروع منفصل بعد استقرار الإصدار: نسخ كاملة، توافق الإضافات والمفاتيح والأدوار وAuth/Storage، تجربة pg_upgrade والرجوع، ثم شركة واحدة كل مرة.
- معالجة الفروق التاريخية لكل شركة بملف حالة وموافقة وقيود هوية وبصمة وملف رجوع وأثر تدقيق. بعد ذلك فقط قرار أرشفة/حذف الملفات الزائدة بناءً على فهرس اعتماد.
